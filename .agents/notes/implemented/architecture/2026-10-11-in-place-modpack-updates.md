# Agent Note: 以版本差异就地更新 Modpack

Status: implemented

## 问题

Minecraft 的 Mod 整合包以 MultiMC 规范打包成 zip 发布。发布新版本的方式是重新打包一个完整的 modpack.zip；对已经用旧版本游玩过的玩家和服主来说，拿到新版本只是开始，把既有客户端/服务端变成新版本才是成本所在。

GTNH 的[安装及更新游戏](https://gtnh.huijiwiki.com/wiki/安装及更新游戏#更新整合包)文档给出了两种更新办法（迁移到新实例、直接更新现有实例）。两者都要求用户自己判断哪些文件该保留、哪些该被新版本覆盖，再手工完成全部搬运；漏搬 usercache.json 会清空玩家背包，改过的配置被覆盖后不可逆，因此官方要求更新前必须备份、跨大版本逐级更新。

问题的本质不是缺少传输工具，而是两点信息在用户侧不可得：新旧版本之间究竟新增、删除、修改了哪些文件，只有打包者的 diff 知道；而用户自己的数据与上游发布的内容混在同一棵目录树里，人工无法可靠区分。于是每次更新都在重复一次高风险的手工分类。

## 决策

modpack-updater 把更新变成一次发布与一次订阅：发布者把自己实例（客户端或服务端）目录中受追踪的变更发布到云端，订阅者获取变更并应用到自己的实例上，取代下载完整整合包、重建实例与手工搬运。

它的用户身份只有两个——发布者与订阅者。发布的内容是 client、server 还是其他实例，用 TAG 区分；服主与玩家的差异只是实例目录的内容不同，不构成两类用户或两套流程。

交付形态是 Java CLI（Java 17，Gradle 构建，入口 io.github.deshark42.modpackupdater.Main），三个命令：init 铺出工作区骨架，publish 发布一个 tag，update 把某个 tag 的更新应用到当前实例。它通过 Prism Launcher 的 pre-launch command 在实例启动前执行。

发布内容在对象存储中的布局见[对象存储布局](2026-10-13-object-storage-layout.md)，发布侧约定见[发布者工作区与发布命令](2026-10-13-publisher-workspace.md)，订阅侧约定见[订阅者工作区与更新流程](2026-10-14-subscriber-workspace.md)，清单与连接配置的字段见[发布内容格式与连接配置](2026-10-14-release-manifest-and-config.md)。

## 曾考虑的替代方案

**保持现状：重新下载完整整合包并人工重建实例。** 这是上游发布方式与 GTNH 官方说明的既有做法，本方案要消除的正是它：整合包体积达数 GB，每次更新都要重新下载；重建实例后仍然要人工搬运全部用户数据。

## 后果

- 订阅者能在既有实例上应用发布者的更新，随后直接进入原有存档，不需要重新下载完整整合包、重建实例或手工搬运。
- 更新只触碰发布清单里出现的路径：用户数据与本地改动不在其中，清单之外的路径也永不进同步范围；清单之内被本次改动的路径会覆盖玩家修改，旧内容只进 backup、不做合并（见[订阅者工作区与更新流程](2026-10-14-subscriber-workspace.md)）。
- 服主与玩家、client 与 server 共用一套流程与配置字段定义，差异只在实例目录的内容。
- 更新范围完全由发布者手工维护的 base/、overlay/ 与 remove.txt 决定（见[发布者 overlay 目录与 base 删除清单](2026-10-14-publisher-overlay.md)）：多放、少放或误把用户数据放进去都会被原样发布出去，remove.txt 写错则会删掉订阅者实例里的文件。
