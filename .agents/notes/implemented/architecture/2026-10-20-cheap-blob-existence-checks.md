# Agent Note: 降低发布时的 blob 存在性检查成本

Status: implemented

## 问题

发布时，工具在传输每个块与块表前都会向对象存储确认它是否已经存在，已存在就跳过上传。这个确认按去重后的块与块表逐个进行，而对象存储把这类读取请求按次计费：一次发布里每个块都要确认一次，即使全部命中，也要同样多次请求；块越多、发布越频繁，费用越高。跳过上传本来是为了省带宽和流量，结果保留下来的却是随块数线性增长的请求账单。

`blob/` 与 `index/` 的布局让这个判断可以更便宜：块与块表按内容哈希寻址，且只增不改不删（[对象存储布局](2026-10-13-object-storage-layout.md)），因此「对象存在」与「内容已经在桶里」等价。同一个工作区反复发布时，同样的块会被反复确认，而它们一旦确认过，内容就不会再变化。分块与块表的来源见[按内容定义分块传输发布内容](2026-10-22-content-defined-chunked-transfer.md)。

目标：在保持跳过语义与发布顺序不变的前提下，让同一个块或块表在工作区里最多向存储确认一次，常规发布接近零请求。

## 决策

在工作区持久化一份只追加的本地缓存，记录已确认存在的块与块表（可随时删除整份，不属于发布内容）。确认一个块或块表是否存在的流程固定为三步：先查缓存，命中即视为存在，跳过上传；未命中则发 HEAD 询问存储，存在则跳过；不存在则上传。HEAD 返回存在和上传成功都在发生时立即写入缓存，写入只追加，不重写、不单独删除。

- **只记录存在**：缓存中出现的块或块表视为存在；不出现只表示未知，绝不表示不存在。因此缓存不完整、并发写、写入丢失只会多确认几次，不会误跳过。
- **立即且原子写入**：HEAD 返回存在时，立即把它追加进缓存；块或块表上传成功后同样立即追加。每次「确认存在 → 写入」「上传成功 → 写入」都在同一把锁内完成，不会覆盖已有条目，不等到发布结束再统一保存；崩溃最多留下半行记录，下次读取会整份丢弃并重建。发布中途失败时，已经写入的条目仍然有效，未完成的块下次重新确认。
- **只追加**：缓存条目只增加，从不修改、也不单独删除；失效只能通过丢弃整份缓存处理。
- **何时丢弃**：桶的位置（endpoint、bucket、prefix）变化、缓存损坏或超过有效期（默认 30 天，可在 publish 命令上调整）时，丢弃整份缓存；之后所有块与块表按同一流程各确认一次。
- **不参与其他环节**：缓存只用于跳过判断；它不决定发布内容，也不参与清单、顺序或订阅者侧。
- 多工作区/多机各自维护缓存：互不知情只会带来重复确认或重复上传，不影响正确性。

缓存是工作区的 `.modpack-updater/known-blobs.jsonl`，JSON Lines，一行一条：第一行是头部 `{"version": "v1", "fingerprint": "<endpoint、bucket、prefix 拼起来的 SHA-256>", "createdAt": <秒级 epoch>}`，之后每行 `{"hash": "<64 位小写十六进制>"}`，块哈希与块表 id 同形。头部把文件绑定到一个桶位置，追加前在锁内复核它，因此同工作区的多个发布者不会把条目写进别的桶位置的缓存。

没有特殊的启动状态：缓存不存在或为空时，流程不变，只是每个块或块表都会走一次 HEAD。成本因此是每个块或块表在工作区里最多一次确认：常规发布只对新增的块与块表产生请求，最理想时为零；丢弃缓存后的一次性请求量与需要的对象数相同，不会比优化前更差。发布已有的并发度可以并行确认，缩短等待。

不新增连接配置字段；release 已存在检查仍保留（每次发布一次请求，可忽略）。

## 曾考虑的替代方案

用分页列举 `blob/` 与 `index/` 前缀预先填充缓存，让之后的发布不再逐项 HEAD。列举按页计费、成本随桶内对象总量增长，还需要列举权限以及分页、XML 解析的实现，而缓存已让 HEAD 对同一个块只付一次，收益不足以抵消这些代价，所以不采用。

## 后果

缓存覆盖本次全部所需块与块表时，存在性检查不产生任何请求；缺少某个块时恰好对它发一次 HEAD；发布中途失败时保留失败前已确认存在或上传成功的条目，失败的上传不进入缓存；缓存被丢弃后，未记录的块与块表各确认一次，未知对象不会被当作存在而跳过。dry-run 不产生网络请求、不改缓存；已存在 release 的报错、跳过/上传计数、写入顺序与清单字节都不受缓存影响。

最大的风险是缓存变成本地正确性依赖：桶被外部清空或删掉个别块或块表、而本地缓存仍记着它们时，发布会跳过上传并写出引用缺失块或块表的 release，问题要到订阅者下载时才暴露。缓解手段是只记录存在、过期丢弃，以及删掉整份缓存即可；但最终仍依赖「blob/ 与 index/ 只增不改不删」的约定，这是本方案有意接受的代价。

缓存条目按块与块表计数，数量级从文件数变成块数：块只增不删，条目跨发布累积，缓存体积随之增长；多工作区各自维护，可能重复确认或重复上传，语义安全但成本略增。
