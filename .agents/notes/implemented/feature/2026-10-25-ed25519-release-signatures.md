# Agent Note: Ed25519 发布清单签名

Status: implemented

## 问题

块、块表与整文件的哈希只能证明下载内容与清单一致。能控制对象存储或 CDN 的写入者可以同时替换清单和全部哈希，订阅者便会把未授权的模组当成正常更新。S3 SigV4 认证客户端的请求，并不向订阅者证明某份 release 经发布者批准。

## 决策

发布签名强制启用，无无签名回退或跳过选项。`security.ReleaseSigning` 使用 Java 17 内置 Ed25519；私钥为未加密 PKCS#8 PEM，公钥为 X.509 SubjectPublicKeyInfo PEM，与 OpenSSL 的 Ed25519 格式兼容。清单结构仍为 version 2，签名独立存于 `metadata/<tag>/releases/<id>.json.sig`，是原始 64 字节值。

签名覆盖清单压缩前的 UTF-8 原始字节。发布只序列化一次，签署成功后才开始上传内容，清单以原字节 gzip 存储，随后上传签名，最后写 latest。签名和清单同样不可变并使用长期缓存头；签名上传失败不推进 latest，已落盘的 release id 不会被重用。订阅者对解压后的原字节先验签、再解析 JSON，并要求签署的 tag 和 release_id 与请求一致，防止跨 tag 或版本的有效签名替换；验证完成才解析路径、请求块表和内容块、拼装与应用。

`Config` 的 `signing_private_key` 与 `trusted_public_key` 分别用于发布签署与订阅验签，默认是 `.modpack-updater/keys/release-private.pem` 与 `release-public.pem`。可指定工作区外的绝对路径；位于工作区内的密钥必须保存在受保护的状态目录，检查也考虑实际路径，不能经别名把可更新文件当作信任根。订阅端检查两条配置路径的位置，但只加载公钥，不要求私钥存在；尚不存在的密钥及其父目录别名遵循[更新器本体与信任根保护](../bug-fix/2026-10-26-protect-running-updater-and-trust-root.md)。配置补默认值不会生成密钥。订阅者公钥由操作者通过可信渠道安装，不从服务器发现或自动信任。

`keygen` 命令只在本地生成默认位置的一对密钥，不依赖有效 S3 配置、不覆盖任何既有密钥、不打印密钥内容；公钥指纹是 SPKI DER 的 SHA-256。POSIX 私钥创建权限为 `0600`，Windows 使用继承的 ACL。公钥写入失败时清理本次刚创建的私钥。密钥部署及升级步骤见 [README](../../../../README.md)。

[对象存储布局](../architecture/2026-10-13-object-storage-layout.md)、[清单与配置格式](../architecture/2026-10-14-release-manifest-and-config.md)、[订阅者流程](../architecture/2026-10-14-subscriber-workspace.md)和 [CDN 读取](../architecture/2026-10-25-cdn-read-endpoint.md)继续持有独立的格式、传输和状态语义，只部分增加认证与对象顺序约束，无记录被完整取代。[状态命名空间](../bug-fix/2026-10-25-reserve-updater-state-paths.md)和[链接保护](../bug-fix/2026-10-25-reject-workspace-link-redirections.md)继续保护本地信任配置，不能由签名取代。

## 曾考虑的替代方案

**缺少公钥或签名时兼容无签名更新。** 不采用：攻击者删除签名即可触发降级，配置遗漏也会让用户误以为已经受保护。旧发布必须重新发布，旧订阅器需明确升级。

**只校验 SHA-256 或依赖 HTTPS / S3 请求签名。** 不采用：存储侧可同时改写清单和内容，HTTPS 只认证连接到的服务器，SigV4 只认证存储请求；它们不等价于独立保存的发布私钥。

**解析清单后重新序列化再验签。** 不采用：会把字节契约绑在某个 JSON 序列化实现上，也在认证前解析不可信内容。签署确切原字节避免字段排序、空白和换行歧义。

**每个模组单独签名或要求玩家安装 OpenSSL。** 不采用：清单已经通过哈希引用全部内容，一份签名足以认证整个 release；Java 已有标准实现，外部工具增加部署依赖。

## 后果

- 新订阅器要求本地公钥与 release 签名，未签名历史 release 不能再应用；旧订阅器忽略新增签名对象，不能自动获得保护。
- 新版本的签名不能授权不同 tag 或 release id。已应用的同版本无操作仍只读取 latest，不重复下载清单。本地旧清单仍是受保护的本地状态，不保存或复验其远端原始签名字节。
- `ReleaseSigningTest` 用 RFC 8032 的独立已知向量验证算法与原字节语义；命令测试覆盖公钥独立更新、篡改清单与签名、缺签名、错误公钥、身份替换、缺密钥及签名上传失败，并断言没有内容下载、文件替换或指针推进。
- latest 未签名，签名不证明新鲜度，不防合法旧版本重放、隐藏更新或拒绝服务；也不证明发布者签署的模组安全。版本 id 没有全序，防回退和签名元数据到期机制不在本次协议中。
- 当前每个工作区一个可信公钥，不提供自动轮换、撤销或多签名；换钥需独立可信渠道部署，旧钥历史版本随之不能应用。未加密私钥的备份与机器访问控制由发布者负责。
