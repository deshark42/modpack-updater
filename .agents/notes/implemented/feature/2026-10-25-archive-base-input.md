# Agent Note: 压缩包 base 输入

Status: implemented

## 问题

官方整合包通常以 ZIP 或 7z 下载，要求发布者先手工解压到 base/ 才能发布，会把重复的准备步骤留给操作者。需要让压缩包与目录表达同一个 base 内容，而不改变 overlay、删除规则、订阅者或对象存储格式。

## 决策

每个 tag 从 `<tag>/base/`、`<tag>/base.zip`、`<tag>/base.7z` 中选择一个 base 来源。原目录工作流不变；一个压缩包可以与 init 创建的空 base/ 并存。空目录指没有任何直接子条目，包含空子目录也不算空。两个压缩包并存，或压缩包与非空 base/ 并存，均在访问存储前报错，避免发布者误把旧内容当成新包。候选路径的错误类型或链接不被当成“缺失”忽略。没有新增 CLI 参数或配置字段。

压缩包保留全部相对路径，不自动去除单一外层目录，也不展开内部 jar、zip 等文件。Apache Commons Compress 读取 ZIP / 7z，显式携带 XZ 运行时依赖以支持常见 7z 的 LZMA / LZMA2，不调用系统 7z 或 unzip。

压缩包在 `.modpack-updater/tmp/` 下的唯一专属目录中按条目流式展开；该目录保留到整个 publish 返回，因为分块只记录源文件位置，上传时还会重新读取对应区间。正常成功或异常退出均清理该目录，不改写原压缩包或 base/，也不清理更新器的 tmp/blob、tmp/file 或其他发布任务的内容。

解包路径校验与发布路径校验分开：前者拒绝绝对路径、盘符、反斜杠、空路径段、`.` / `..` 段、重复条目、文件与目录冲突，以及链接、特殊文件和不支持的条目；ZIP 条目名必须严格按 UTF-8 解码，未带 UTF-8 标志、且没有该字段、名字字节也不是合法 UTF-8 的旧式编码名称会被拒绝，因为库的替换式解码会把它静默变成乱码路径，而带 Info-ZIP Unicode Path 扩展字段的条目改用该字段，字段载荷同样必须严格按 UTF-8 解码，否则整包拒绝；真实文件系统访问继续经过 [PathGuard 边界](../bug-fix/2026-10-25-reject-workspace-link-redirections.md)。ZIP 内容显式核对长度与 CRC，损坏或不可读压缩包使整次发布在上传前失败。解包器不因为条目位于保留名称空间就提前过滤；[状态路径保护](../bug-fix/2026-10-25-reserve-updater-state-paths.md)仍由 remove 与 overlay 合并之后的有效路径校验持有，因而被 remove 排除的状态路径与目录 base 保持相同语义。

本记录扩展 [发布者工作区](../architecture/2026-10-13-publisher-workspace.md)的 base 来源与内容临时文件事实，不取代该记录的配置、命令及发布生命周期约定；[overlay 与删除清单](../architecture/2026-10-14-publisher-overlay.md)继续持有与来源无关的合并规则。上述记录及两个安全记录均有独立的未来指导价值，保留活跃，没有完整取代或应封存的记录。

## 曾考虑的替代方案

**增加 publish --base <path> 或每 tag 的配置。** 可保留任意下载文件名，但增加 CLI 或持久化输入约定；当前固定的 base.zip / base.7z 与目录约定一致，足以消除手工解压，不扩大配置面。

**直接从压缩流分块和上传。** 不采用：当前去重规划与实际上传分开，Placement 在上传时随机重读源文件；7z 的 solid 数据又不适合按块重复随机解压。先物化目录能复用现有分块、去重和并发上传，不把压缩源概念带进存储协议。

**把压缩包解压进 base/ 并持久保留。** 不采用：失败时会留下新旧混合树，无法判断 base/ 是否陈旧，还可能覆盖发布者自行维护的输入。专属临时目录只服务一次发布。

**自动剥掉唯一的顶层目录或在多个来源中设优先级。** 不采用：这会静默改写清单路径或选错官方包，订阅者可能因此删除原路径；保留原树并拒绝冲突更明确。仅容许 init 的空 base/ 不会丢失任何输入。

## 后果

- 发布者只需替换压缩包，overlay 与 remove.txt 保持独立；目录输入和云端发布格式不变。
- 每次压缩包发布都需要完整解压一次，以及足以容纳解压内容的额外本地磁盘空间；没有跨次解压缓存。解包是顺序读取，不把整份解压内容装入内存。来源校验与解包在任何存储访问之前完成，因此已存在版本号等存储侧错误要到解包之后才报告，重复发布会多付一次解包成本。
- 不支持加密、多卷或库不能读取的压缩包；不提供密码输入或调用外部命令的回退。Commons Compress 也不支持 7z 的多输入/输出流编码链，例如 7-Zip 针对可执行文件的 BCJ2 过滤器：用官方 7-Zip（7z2301-extra.7z 实测）打包含 exe 的目录即会整包报错，错误信息保留库原文并带压缩包路径，用户需改用 ZIP 或关闭该过滤器。7z 解码器内存上限为 256 MiB，拒绝需要更大字典的输入，避免畸形元数据请求近乎无限的解码内存。7z 条目名按 UTF-16 解码，库对不成对的代理项做替换解码；头部校验自洽的人造包可能得到含 U+FFFD 的名称，该名称仍是合法路径且在发布者与订阅者间一致，因此不额外拒绝。没有新增全包大小上限，发布者仍须信任输入并准备足够资源；路径与条目校验不等于对压缩炸弹的完整资源隔离。
- 成功与异常退出都会清理 staging；进程被强制终止或清理自身失败仍可能留下临时内容。PathGuard 不承诺抵御另一个本地进程并发替换路径。
- 来源名区分大小写：只有确切的 `base.zip` / `base.7z` 被采用，`base.ZIP` 一类变体会报错而不是被忽略。解包校验不检测大小写不敏感或 Unicode 归一化后同名的条目（如 `mods/A.jar` 与 `mods/a.jar`）：这类冲突在 `CREATE_NEW` 处失败，仍属失败关闭，只是报错发生在解包中途；Windows 设备名与结尾点/空格同样由发布前的路径校验拒绝，而非解包时提前拒绝。
- BaseArchiveTest 持有真实 ZIP / 7z 解包、UTF-8 名称接受与旧式编码名称拒绝、危险条目、内容校验和清理的单元覆盖；BaseSourceTest 持有来源选择矩阵与大小写变体拒绝；PublishTest 覆盖归档与 overlay / remove 的接线和发布前失败无存储副作用。
