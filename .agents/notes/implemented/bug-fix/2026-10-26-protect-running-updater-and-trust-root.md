# Agent Note: release 不得接管更新器及本地信任根

Status: implemented

## 问题

发布签名证明某份 release 获得发布者授权，却不应授予发布者改写订阅者验签程序及信任来源的权限。状态目录已有保留命名空间，但正在运行的更新器可能位于实例任意位置；清单既能替换文件，也能把整个旧目录移入备份。只禁止某个固定 JAR 名称或只检查新下载项，仍会留下重命名、父目录删除和未变条目等绕过方式。

## 决策

[UpdaterProtection](../../../../src/main/java/io/github/deshark42/modpackupdater/security/UpdaterProtection.java) 根据加载的 `Main` 的 protection domain / code source 定位实际代码，不接受发布内容或配置指定受保护位置。以 JAR 运行时保护实际文件；以 classpath 运行时保护实际 classes 目录。无法定位或解析本地代码位置时拒绝更新，不静默跳过。

清单路径与代码位置相同、是其祖先或后代时均拒绝，比较使用路径段而非字符串前缀。检查以工作区根的实际位置为基准，保留用户主动选择根目录链接的能力；根以下继续使用现有链接与原生别名检查。已有文件与更新器具有相同文件身份的硬链接也保守拒绝：这是所有权限制，不是声称原子替换一个硬链接必然改写另一个链接的 inode 内容。

[Update](../../../../src/main/java/io/github/deshark42/modpackupdater/command/Update.java) 在会变更的运行中检查全部本地旧清单，在验签及身份匹配后检查全部目标清单，而不是只检查 diff；目标 release 已应用时在读取旧清单之前提前返回，无操作运行不预检任何清单（[release 已应用时不再预检旧清单](../simplification/2026-10-27-skip-preflight-when-release-is-already-applied.md)）。失败发生在请求块表与内容块、暂存、备份和应用之前；不能借删除旧条目、相同哈希或本地已有相同内容绕过。

本地信任配置仍由[状态命名空间](2026-10-25-reserve-updater-state-paths.md)、[发布签名](../feature/2026-10-25-ed25519-release-signatures.md)和[链接保护](2026-10-25-reject-workspace-link-redirections.md)共同持有。它们分别记录保留状态、认证协议和文件系统访问规则，本记录只扩展更新器本体保护并补全密钥位置检查，没有完整取代任何一份记录。

每次 `UpdaterProtection.require` 对完整清单执行只读预检，复用 `PathGuard.inspectAll` 已读的末端属性，不重复执行 `exists`。更新入口按 `concurrency` 将清单分成均衡分片，同时最多 8 个 worker、每片至少 128 条路径；小清单与并发度 1 直接串行检查。各分片共用不可变的受信根，但独立调用 `inspectAll`，不共享可变的属性和真实路径缓存。分片内部首次需要文件身份比较时才读取一次当前更新器属性；只有已知的普通文件/目录类型不同才能排除同一文件，其余情况仍执行 `Files.isSameFile`。不按大小过滤：即使 `BasicFileAttributes` 来自磁盘，Windows 的快速属性读取仍可能返回硬链接目录项的旧大小。也不依赖可为空的 `fileKey`。更新器属性与路径快照均不跨清单缓存；路径段的双向祖先检查始终先于身份过滤。

并行只重叠文件系统等待：每条路径仍读取其全部已存在路径段的属性、比较最深现存目录的真实路径，并在需要时比较文件身份；普通文件叶子自身不再解析真实路径（[目录级真实路径解析](../simplification/2026-10-27-resolve-one-directory-per-preflight-path.md)）。专用 executor 只提交每个分片一个任务；成功时等待全部分片，发现失败或调用线程中断时请求取消剩余工作并等待所有 reader 结束，随后恢复调用线程的中断状态。按提交顺序等待分片，不保证立即发现后续分片的失败；普通文件系统调用和路径遍历未必响应线程中断，不能把取消请求当作 reader 已经停止；方法返回前不允许遗留读取进入应用、后续 tag 或下一轮检查。

`Config` 对尚不存在的密钥也解析其最近可解析祖先，再接回缺失后缀，避免配置在工作区外的路径经已存在的链接父目录实际落入可发布内容。不可解析的现有链接不当作普通缺失目录放行。`update` 检查公钥和私钥的配置位置，但只加载公钥；订阅者无需持有私钥。工作区内的密钥仍必须在状态目录中，工作区外的正常密钥仍可使用。

## 曾考虑的替代方案

**只禁止固定更新器文件名。** 不采用：用户可以重命名或移动 JAR，也可能从 classpath 运行；保护实际加载的代码位置才与执行权限一致。

**只检查下载集合，或签名有效就允许自更新。** 不采用：旧清单删除、父目录替换与同哈希跳过都可能绕过下载检查；有效签名不等于订阅者同意把程序和本地信任根的控制权交给 release。

**按大小、扩展名或可选的 fileKey 省略文件身份检查。** 不采用：清单大小不代表当前本地文件，硬链接可以声明任意大小；[NTFS 的硬链接目录项可能保留旧大小](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions)，[Windows JDK 的普通属性读取](https://github.com/openjdk/jdk17u/blob/master/src/java.base/windows/classes/sun/nio/fs/WindowsFileAttributes.java) 缺省使用快速目录项信息，因此两个硬链接即使没有并发写入也可能读到不同大小。强制准确 metadata 又会重新增加逐文件打开。扩展名与代码所有权无关，平台也未必提供 fileKey；只保留已知类型不同的排除，其余继续原来的身份检查。

**用目录枚举的名称替代逐文件真实路径比较。** 暂不采用：Windows 长名称可以减少共同祖先的原生查询，但必须另行证明设备名、NT-native 结尾点/空格、8.3 别名及 reparse 状态的边界；它也不能证明 hardlink 身份。当前改为只比较最深现存目录的真实路径（[目录级真实路径解析](../simplification/2026-10-27-resolve-one-directory-per-preflight-path.md)），仍不使用目录枚举名称，避免为性能引入新的平台专属名称证明。

**直接复用传输的 Parallel helper。** 不采用：该 helper 取消线程池后不等待 worker 终止；预检必须在返回前完成 reader 清理，因此使用仅作用于清单预检的有界 executor，不改变传输生命周期。

**额外禁止所有脚本或可执行扩展名。** 不采用：启动脚本可能是合法整合包内容，模组本身也执行代码；扩展名黑名单不能提供沙箱，也不能代替更新器与信任配置的权限边界。

## 后果

- 无绕过选项；冲突使当前 tag 失败，不静默过滤清单。已有冲突的本地记录需由操作者修复；更新器升级及公钥更换通过独立可信渠道完成。
- 工具仍可维护自己的状态、运行日志与缺省配置字段；批量更新中此前成功的 tag 不回滚。
- 单元测试覆盖真实代码位置、改名及空格、双向路径前缀、classes 目录、外部代码、硬链接、工作区根链接及缺失密钥父目录，也验证清单大小与真实硬链接不符时仍拒绝、等长普通文件可用、硬链接建立后再调整更新器大小仍拒绝，以及同一保护器下一次调用发现被替换的硬链接。命令测试覆盖有效签名的冲突、内容已匹配、旧清单删除/未变、信任配置与密钥命名空间，并检查受保护文件、普通文件、状态和请求序列；目标 release 已应用的无操作跳过由[已应用 release 的跳过](../simplification/2026-10-27-skip-preflight-when-release-is-already-applied.md)持有。
- 分片会至多重复 8 份共同祖先 metadata，以重叠 Windows 的逐文件等待；不是减少系统调用数的保证。存储设备或过滤驱动可能串行化元数据操作，不能承诺各环境的加速倍数。测试使用 latch 验证并发上限、全量且不重复检查，以及失败和中断后的 reader 清理；大份旧清单在会变更的运行中仍必须在任何变更前失败；目标 release 已应用的无操作运行不读取该旧清单（[已应用 release 的跳过](../simplification/2026-10-27-skip-preflight-when-release-is-already-applied.md)）。
- 不是本地并发路径替换的锁，也不是脚本或模组沙箱；受信发布者仍能更新合法的模组与启动脚本。
