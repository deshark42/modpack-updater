# Agent Note: 按内容定义分块传输发布内容

Status: proposed

## 问题

发布内容在对象存储里按内容哈希寻址：`blobs/` 下一个对象就是一个文件的完整内容，清单把路径记成 `{hash, size}`（见[发布内容格式与连接配置](../../implemented/architecture/2026-10-14-release-manifest-and-config.md)）。去重因此只在「整个文件的字节完全相同」时生效：同一份文件出现在多个 tag 或多次发布里只存一份，但只要有一个字节不同，它就是另一个新的对象。

整合包更新恰好落在去重的反面。官方发布新版本时，被改动的文件数量通常不多，但每个改动的文件都是「大部分字节相同、局部不同」——Mod 的 jar 更是如此，几万个压缩条目里往往只有少数几个类、语言文件和资源被替换。文件级哈希看不到这一点：哈希一变，整份内容就是新的。

三个 GTNH mod 的相邻两版可以量出这个差距：文件体积几乎不变（46.2MB、64.9MB、24.2MB，各自前后差几千字节），按 jar 条目比较只有约 5.2MB 的压缩内容真正变化，约 4%；但按文件哈希，135.3MB 全是新内容。于是每次官方更新都要完整上传 135.3MB，每个订阅者再完整下载一次，桶里为这两个版本留下 270.6MB。

## 提案

把对象存储里的对象从「一个文件的完整内容」改成「一个文件的一段字节」，文件由块表表达；块边界按内容定义，同一段字节跨版本、跨 tag 只存一次、只传一次。

### 分块

用 CDC（内容定义分块）：gear 滚动哈希逐字节推进，命中切点条件时截断。参数取 min 8 KiB / avg 32 KiB / max 128 KiB：avg 是切点出现的期望间隔，min 之前不允许切，因此平均块长是 min + avg（约 40 KiB）而非 avg；min 挡的是全零、填充、周期性内容引发的病态短块，max 截的是长块。

- 边界只由文件的字节决定，因此同一份内容在任何机器、任何 tag、任何版本下切出同一串块；插入或删除只影响邻近的几个块。
- 块的标识是块内容的 sha256，`hash_algorithm` 不变。小于 min 的文件整体成一块，空文件是零块，因此配置、清单这类小文件的行为与今天一致。
- 实测（三个 GTNH mod 的相邻两版）：新版本独有块 18.2MB / 135.3MB，占 13.5%，块命中率 89.3%。

### 三层结构

- 清单 `metadata/<tag>/releases/<release_id>.json`：`files` 的值从 `{ hash, size }` 变成 `{ hash, size, chunks }`，`hash` 仍是整文件 sha256，因此「比较两份清单得出动哪些路径」的模型不变。
- 块表 `index/<哈希前两位>/<index_id>`：一份文件内容的有序块列表，本身也内容寻址，同样的文件内容只有一份块表。
- 块 `blob/<哈希前两位>/<chunk_id>`：一段字节，路径规则、两位分片、只增不改不删都不变。

块表对象形如：

```json
{
  "version": 1,
  "algorithm": "cdc-gear",
  "chunking": { "min": 8192, "avg": 32768, "max": 131072 },
  "size": 48448437,
  "chunks": ["3f2a…", "9b07…"]
}
```

- `index_id` 是块表序列化后的 sha256；块表记录切块参数，订阅者据此切分本地旧文件，清单不必重复这些参数。
- 清单里每个文件只多一个 64 位十六进制字段，块表的体积不进入清单。

### 发布与更新

只记分块改变的环节，其余流程沿用既有记录。

- 发布：写入顺序为 块 → 块表 → 清单 → latest。发布者不需要旧版本文件，同一段字节只要曾经发布过本次就自动命中，「发布侧不与上一版比较」不变。
- 更新：`Plan` 仍只比较两份清单的 `hash`；对被替换的路径，切分 `backup/` 里的旧副本得到本地已有的块，只下载缺失块、按序拼装，再校验整文件 sha256。
- 读本地旧文件只用于跳过下载，不改变动哪些路径的判断；玩家改过的文件也能按内容部分复用，备份副本缺失或读失败就当没有本地块，退化为全量下载。
- 跳版没有代价：块表不引用其他 release。`known-blobs.jsonl` 的格式不变，条目从文件变成块与块表。
- `config.json` 不新增字段，`concurrency` 仍是唯一的并发参数，含义从同时在传的文件数变为同时在传的块数。

### 不保留 v1 兼容

工具尚未被使用，因此不为 v1 留分支：目录直接改名，桶里旧的整文件对象不迁移、不识别。清单仍升到 `version: 2`，让残留的旧工具与旧清单在第一次读取时就报错，而不是按 v1 读出一个能跑但慢的结果。

## 曾考虑的替代方案

定长分块，按固定字节长度切块，块边界只取决于文件内的偏移。插入或删除会让后续所有块整体错位，实测三种块长的命中率都是 0%，等于分块了但没有去重，还额外付出块表与对象数。

整文件二进制 delta（git 式），以旧版本的整文件作为 base object 保存 delta 指令流，新文件由旧文件加若干 copy/insert 指令还原。它需要 base object，每个 release 因此不再独立可读，跳版要沿 delta 链回溯到某个 base 或退回全量下载，追加型存储也无法 repack 重组依赖；git 的 thin pack 还要 have/want 协商，而 S3 的 `GET`/`PUT` 没有这个通道。

全局索引 + pack（restic 式），把块连续追加进较大的 pack 对象，用全局索引记块位置、靠 Range 读取。它的索引可变、可 rebuild、整体载入内存并依赖 prune 回收空间，这些前提在追加型存储里都不成立；最贴合追加型存储的形态是每 release 一个只含新增块的 pack，但那仍要重新设计索引层，所以第一版推迟而非否掉，等首次全量的请求延迟或请求成本不可接受时再重新考虑。

tree 化清单（restic 式目录树），把扁平清单换成目录树，一个文件改动只重写父目录链。它能解决清单体积，但会推翻「两份清单相减」这个已记录的更新模型，代价大于收益。

维持现状，不切分，继续按整文件上传与下载。每次发布都整份重传、存储随发布次数增长，这正是本提案要消除的。

## 验收标准

- 只改一个文件的发布：上传字节约等于该文件的变化块字节 + 块表 + 清单；未变化的文件不产生任何块上传。
- 订阅者从上一版更新到该版本：实际下载字节约等于变化块字节 + 块表，且与日志报出的复用块数一致。
- 每个文件拼装后 sha256 等于清单里的 `hash`；块表内的 `size` 等于清单中的 `size`。
- 同一份文件内容出现在两个 tag 或两次发布中时，块表与块都只写一次。
- `--dry-run` 不联网、不写盘、不切分本地文件，报出的仍是上界。
- 首次更新（无本地旧文件）退化为全量下载而不失败。

## 风险

使用 CDC 产生的对象数相比内容哈希寻址要变得更多。全量下载的请求数随之增加，小对象的往返让首次更新变慢；本地缓存条目也一起变多，过期后重建要重新确认；任一对象被外部删除或损坏，所有引用它的 release 都拼装失败，并且要到拼装时才暴露。
